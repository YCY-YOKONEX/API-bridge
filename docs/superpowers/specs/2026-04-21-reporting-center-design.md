# 综合报表中心设计文档

## 1. 背景与目标

当前系统已经具备基础统计与监控能力，但统计入口分散在 `Dashboard`、`Monitor`、`Logs` 三个页面中，存在以下问题：

- 指标分散，管理员和运营需要在多个页面之间切换
- 接口粒度偏碎，前端需要分别请求实时统计、趋势、日志、系统指标
- 统计口径不统一，难以支持导出、摘要和后续扩展
- 现有页面更偏“监控页”与“日志页”，还不具备完整报表中心能力

本次目标是在现有系统上建设一个统一的“综合报表中心”，服务两类主要角色：

- 管理员 / 运维：关注系统稳定性、连接情况、错误与资源使用
- 运营负责人：关注消息量、活跃用户、指令调用、趋势变化和异常波动

目标能力包括：

- 单页报表工作台
- 全局统一筛选
- 实时 + 历史统计分析
- 用户 / 指令 / 时间 / 系统多维筛选
- 图表、排行、明细、摘要同屏联动
- Excel / CSV 导出
- 周报 / 月报摘要生成

## 2. 设计原则

### 2.1 单一入口

新增独立的报表工作台页面，作为完整统计分析入口。已有 `Dashboard`、`Monitor`、`Logs` 继续保留，但不再承担完整报表中心职责。

### 2.2 统一查询上下文

报表页面所有模块共享同一份查询条件，包括时间范围、聚合粒度、用户筛选、指令筛选、系统筛选。所有图表、排行、明细、导出和摘要都基于相同上下文生成。

### 2.3 聚合优先

后端新增报表聚合层，避免前端直接拼装多个零散接口结果。前端只感知“报表数据模型”，不感知底层日志表和统计函数细节。

### 2.4 分层演进

先完成可用的报表底座，再逐步增强结构分析、摘要和导出能力，避免一次性做成重型 BI 系统。

## 3. 用户场景

### 3.1 管理员 / 运维

- 查看当前在线用户、连接数、错误率、响应时间
- 排查某个时间段内的错误高峰和资源异常
- 查询指定用户或指令的失败情况
- 导出某个时段的系统与调用明细用于排障或审计

### 3.2 运营负责人

- 查看消息量、活跃用户、指令调用趋势
- 识别高频用户、高频指令、失败高发时段
- 分析不同时间范围内的波动与变化
- 导出运营周报 / 月报摘要用于汇报

## 4. 页面结构

综合报表中心采用“单页大报表工作台”结构，自上而下分为 6 个区域。

### 4.1 顶部筛选栏

统一控制当前报表查询上下文。

字段建议：

- 时间范围：实时、今日、近 7 天、近 30 天、本月、自定义区间
- 聚合粒度：实时 / 小时 / 天 / 周 / 月
- 用户筛选：用户 ID、在线状态、新老用户
- 指令筛选：指令类型、调用状态、耗时区间
- 系统筛选：错误类型、CPU / 内存 / 磁盘区间
- 操作按钮：查询、重置、导出 Excel、导出 CSV、生成摘要

### 4.2 核心概览区

用于第一屏快速识别状态，建议使用指标卡片。

指标建议：

- 在线用户数
- 活跃用户数
- 今日消息量
- 今日指令调用量
- 成功率
- 平均响应时间
- P95 响应时间
- 错误率

每张卡片可扩展：

- 当前值
- 环比值
- 峰值
- 告警状态

### 4.3 趋势分析区

展示随时间变化的主要趋势，用于识别波动、峰值和异常。

建议图表：

- 消息量趋势
- 活跃用户趋势
- 指令调用趋势
- 成功率趋势
- 响应时间趋势
- 错误趋势
- CPU / 内存 / 磁盘趋势

布局建议采用双列卡片式图表矩阵。

### 4.4 结构分析区

展示“构成”和“分布”信息。

建议图表：

- 指令类型分布
- 成功 / 失败占比
- 错误类型分布
- 用户活跃分层
- TOP 用户排行
- TOP 指令排行
- 高失败指令排行

### 4.5 明细区

用于查看可追溯数据，建议使用 Tab 或分段切换。

明细建议：

- 用户行为明细
- 指令调用明细
- 错误事件明细
- 系统资源快照
- 导出记录

### 4.6 摘要区

基于当前筛选条件生成结构化报表摘要，不采用自由文本聊天形式。

建议内容：

- 当前周期核心结论
- 环比变化
- 高峰 / 低谷时段
- 主要异常项
- 建议关注点

## 5. 指标体系

为支持双角色使用，指标建议划分为 4 层。

### 5.1 实时运营指标

强调“当前状态”。

- 在线用户数
- 当前连接数 / 峰值连接数
- 今日消息量
- 今日指令量
- 当前错误数 / 今日错误率
- 平均响应时间 / P95 / P99
- CPU / 内存 / 磁盘当前值与峰值

### 5.2 趋势指标

强调“变化趋势”。

- 消息量趋势
- 活跃用户趋势
- 指令调用趋势
- 成功率趋势
- 响应时间趋势
- 错误趋势
- 系统资源趋势

### 5.3 结构指标

强调“构成与分布”。

- 指令类型占比
- 成功 / 失败占比
- 错误类型占比
- 用户活跃层级分布
- 新老用户占比
- 高频用户排行
- 高频指令排行
- 高失败指令排行

### 5.4 明细指标

强调“排查与导出”。

- 用户登录 / 登出记录
- 指令调用记录
- 单用户调用轨迹
- 单指令时间分布
- 错误事件清单
- 系统资源快照清单

## 6. 关键统计口径

为避免只停留在现有接口拼装，建议额外引入以下核心统计口径：

### 6.1 成功率

支持以下维度：

- 按指令统计
- 按用户统计
- 按时间窗口统计

### 6.2 响应分位数

除平均响应时间外，新增：

- P50
- P95
- P99

用于更真实反映长尾时延。

### 6.3 异常密度

新增以下统计：

- 每小时错误数
- 每百次调用错误数
- 连续失败次数

用于发现“总量不高但风险升高”的问题。

## 7. 数据模型设计

建议新增报表聚合层，并统一前后端报表数据模型。

### 7.1 ReportQuery

统一查询条件对象。

建议字段：

- `presetRange`
- `startTime`
- `endTime`
- `granularity`
- `userId`
- `onlineStatus`
- `userSegment`
- `commandType`
- `commandStatus`
- `latencyMin`
- `latencyMax`
- `errorType`
- `cpuMin` / `cpuMax`
- `memoryMin` / `memoryMax`
- `diskMin` / `diskMax`
- `page`
- `pageSize`
- `sortField`
- `sortOrder`

### 7.2 ReportOverview

用于 KPI 卡片。

建议字段：

- `metric`
- `label`
- `value`
- `unit`
- `compareValue`
- `compareRate`
- `peakValue`
- `thresholdState`

### 7.3 ReportSeries

用于趋势图。

建议结构：

- `metric`
- `granularity`
- `points: [{ time, value, extra }]`

适用于消息量、活跃用户、成功率、响应时间、资源使用等所有趋势图。

### 7.4 ReportBreakdown

用于占比图、分布图、排行图。

建议结构：

- `metric`
- `dimension`
- `items: [{ key, label, value, ratio, extra }]`

### 7.5 ReportDetail

用于明细表和导出。

建议结构：

- `type`
- `columns`
- `rows`
- `pagination`

## 8. API 设计

不建议继续将页面建立在多个零散接口上，而应增加统一报表聚合接口。

建议新增：

- `GET /api/admin/reports/overview`
- `GET /api/admin/reports/trends`
- `GET /api/admin/reports/distributions`
- `GET /api/admin/reports/rankings`
- `GET /api/admin/reports/details`
- `POST /api/admin/reports/export`
- `GET /api/admin/reports/summary`

### 8.1 overview

返回 KPI 卡片数据，用于第一屏总览。

### 8.2 trends

返回趋势图数据，可通过 `metric` 参数指定消息量、错误率、响应时间等。

### 8.3 distributions

返回占比或结构分析数据，例如指令类型分布、错误类型分布等。

### 8.4 rankings

返回排行数据，例如 TOP 用户、TOP 指令、高失败指令排行等。

### 8.5 details

返回明细表数据，支持分页、排序、筛选。

### 8.6 export

根据当前查询条件导出 Excel / CSV。

### 8.7 summary

返回结构化摘要文本和关键洞察，支撑周报 / 月报输出。

## 9. 现有页面重构策略

### 9.1 Dashboard

保留为轻量首页，只展示系统健康概览与关键入口，不继续扩展为完整报表页。

### 9.2 Monitor

保留为实时监控页，偏运维即时观察；图表与统计逻辑逐步复用报表聚合层。

### 9.3 Logs

保留为审计与查询页，适合深查日志明细；底层查询能力与报表明细接口逐步统一。

### 9.4 ReportsWorkbench

新增统一报表工作台，承担：

- 统一筛选
- KPI 总览
- 趋势分析
- 结构分析
- 明细查询
- 导出与摘要

## 10. 推荐实施阶段

### 第一阶段：报表底座

目标：建立统一查询条件、数据模型和工作台基本框架。

范围：

- 新增报表工作台页面
- 统一筛选栏
- 核心 KPI 卡片
- 趋势图模块
- 基础明细表
- 报表聚合接口初版

### 第二阶段：分析增强

目标：补齐结构分析和更有价值的统计口径。

范围：

- 分布图与排行图
- 用户分层
- 高失败指令分析
- P95 / P99
- 异常密度
- 结构化摘要

### 第三阶段：输出能力

目标：完善外部汇报和离线输出。

范围：

- Excel / CSV 导出
- 周报 / 月报摘要
- 导出记录
- 后续可扩展定时报表

## 11. 非目标

本阶段不追求以下能力：

- 自定义拖拽式 BI 编排
- 任意组件拼装与存档
- 多租户复杂权限报表
- 完整数据仓库建设

本次设计目标是建设“统一、可扩展、贴合当前系统”的综合报表中心，而不是一次性做成通用 BI 平台。

## 12. 风险与注意事项

### 12.1 数据源一致性

当前统计数据来自实时状态、日志记录和系统指标，需统一统计口径，否则不同模块之间可能出现数值不一致。

### 12.2 查询性能

时间范围、自定义筛选和明细导出会显著放大查询成本，需要优先考虑聚合查询、索引和必要缓存。

### 12.3 页面复杂度

单页工作台信息密度高，需通过模块折叠、默认展示和异步加载控制首屏复杂度。

### 12.4 导出一致性

导出结果应与当前筛选和页面展示口径完全一致，避免出现“页面看的是 A，导出得到的是 B”。

## 13. 结论

推荐采用“统一报表工作台 + 报表聚合接口 + 分阶段建设”的方案。

具体结论如下：

- 入口形式：单页大报表工作台
- 目标角色：管理员 / 运维 + 运营负责人
- 筛选维度：时间、用户、指令、系统全维度
- 输出能力：在线分析 + Excel / CSV 导出 + 周报 / 月报摘要
- 落地路径：先报表底座，再分析增强，最后导出与摘要完善

该方案既能复用现有系统能力，也能为后续统计扩展、摘要生成和报表沉淀提供稳定基础。
